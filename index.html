01 · Executive Summary

三条关键结论

先看结论，再读细节。以下判断均可在文末参考来源中找到依据。

结论 01

「AI 生成 + 人工验证」是当前唯一量产主流

LLM 写模块级 RTL 已进入企业流程，但「可流片」的最终责任仍由工程师兜底。2026 年的行业共识是：AI 负责提效，人负责正确性与时序收敛。

结论 02

基准成绩很好，工程差距仍大

VerilogEval / RTLLM 上顶级方案通过率已近饱和（97–100%），但真实 RISC-V 全流程评估显示：功能正确率、集成与时序问题仍是硬骨头（IEEE 11570171）。

结论 06

复杂度决定成败：译码器可用，NoC 仍不可靠

四类典型功能呈现清晰梯度——组合译码器（AI 相对擅长）→ 总线矩阵（需仿真裁判）→ Ring（中低可靠）→ NoC（芯片级任务，需层次化+验证优先方法）。接入策略应按复杂度分级（详见「专项」章节）。

02 · Current State

现状：十个月从「工具」走到「端到端」

2025.6 以来的演进主线：精度方法论成型 → Agent 化爆发 → 端到端芯片。注意：语法正确 ≠ 功能正确 ≠ 可流片，三者差距仍是行业核心矛盾。

2025.06 – 09 · 精度方法论成型

推理缩放与自动修复并进

ScaleRTL（2025.6）证明「推理数据 + 测试时计算」可显著提升 RTL 生成精度；ProtocolLLM（2025.6）建立通信协议 RTL 基准，暴露协议类代码对顶级模型的挑战；AutoVeriFix（2025.9）以「生成 + 自动修复」闭环把 VerilogEval-Machine 推到 97–100%。

2025.10 – 12 · Agent 化爆发与范式定型

RAG / PPA 感知 / 自验证 / 综述齐发

DeepV（RAG + 知识库）、LLM-VeriPPA（PPA 感知）、Backtrack-ToT（自解耦自验证）、IBM 可逆逻辑研究（2025.12）密集出现；Synopsys.ai Copilot、Cadence JedAI、Siemens AI 全线商用化。Agentic EDA 综述（2025.12）正式提出「从 Copilot 到 Agent」范式转移；ChipAgents（Alpha Design AI）以 VerilogEval-v2 97.4% 保持 SOTA。

2026 · 端到端与基准升级

从「写代码」到「造芯片」

Design Conductor（2026.3）实现首个「规格 → GDSII」端到端：自主 Agent 12 小时产出 1.5 GHz 可跑 Linux 的 RISC-V；2.0 版（2026.5）80 小时构建推理加速器。VeriGraphi、ChipCraftBrain（2026.4）验证层次化多智能体与验证优先路线；ChipBench（2026.1）接棒已饱和的旧基准；HWE-Bench（2026.4）转向真实硬件 bug 修复；「Closing the Loop」研究聚焦工具反馈 Gap——打通仿真/综合报错回灌成为主线。

研究端：精度方法论成熟

推理时计算（ScaleRTL）、PPA 感知生成（LLM-VeriPPA）、自解耦+自验证（Backtrack-ToT）、RAG（DeepV）四条技术路线并行，模块级功能正确率已从「不可用」提升到「可辅助」。核心范式：生成 → 仿真 → 修复。

产品端：Copilot 已进设计流程

三大 EDA 厂商（Synopsys / Cadence / Siemens）均已提供生成式 AI 助手，覆盖 RTL 生成、文档、回归分析。企业落地方式以「私有化 + 内部代码库 RAG」为主，规避 IP 外泄风险。

实践端：验证先于设计落地

相比直接生成 RTL，业界更早接受的是 AI 生成 testbench/断言/覆盖率补洞——因为验证产出可被现有回归工具自动判定对错，反馈闭环天然存在，风险可控（2025.6 后 AI Agents for UVM 等实践持续落地）。

03 · Deep Dive

专项效果：系统译码 / Decoder / NoC / Ring

针对 SoC 中最常见的四类功能——系统译码（指令/地址译码）、组合 Decoder、NoC（片上网络）、Ring（环形互连）——综合 2024–2026 的基准与案例评估「AI 到底能做成什么样」。核心结论：按「接口数量 × 层次深度」排列，这四类功能构成了一条从 AI 舒适区到深水区的完整梯度。

表 2 · 四类典型功能的 AI 实现效果评估（综合 ProtocolLLM / RISC-V 整机评估 / 2026 多智能体工作等，2026.04）
功能 典型形态 复杂度 AI 当前效果 主要失败模式 建议做法
组合译码器

译码器：AI 的相对舒适区

IBM Research（arXiv:2512.03053）把译码/编码这类「可逆问题」单独研究：输入输出可逆、可被自动验证，因此 LLM 的幻觉与遗漏能被检测并纠正，效果明显优于不可验证的逻辑（SemiEngineering 有专文报道）。RISC-V 处理器全流程评估（IEEE 11570171）则提示：译码逻辑本身不难，难在模块接口与层次约束——这正是工程接入时最需要人工把关的地方。

协议与总线互连：需要专门的裁判

ProtocolLLM（arXiv:2506.07945，UIUC + CISPA）建立了面向通信协议 RTL 的基准（含 UART/I2C/SPI 与 AXI 等片上总线协议），结论：协议代码对顶级模型仍具挑战，功能正确率随协议复杂度明显下降，仿真验证是必要的裁判与迭代驱动力。2026 年的 VeriGraphi、ChipCraftBrain 进一步验证了「先拆层次、再逐模块生成 + 验证优先」路线——大型互连设计不再依赖一次性生成。

NoC / Ring：2026 年的攻坚区

芯片级任务（NoC、处理器核等）的公开评测显示通过率显著低于模块级——NoC 正是「多模块交互 + 层次化」的代表。VeriGraphi、ChipCraftBrain（2026.4）均以「层次化拆分 + 先验证后生成」应对；Design Conductor（2026.3）则用端到端 Agent 证明整芯片可行，但代价是数百亿 token 与强验证闭环。Ring 无专门基准，按复杂度介于总线矩阵与 NoC 之间处理最稳妥：单节点 AI 可写，整环靠组装与定向验证。

梯度法则：模块间接口越多、层次越深，LLM 单次生成的成功率越低——从「译码器≈可用」到「NoC≈不可靠」的落差，本质不是模型智力问题，而是可验证性与接口约束问题。任何复杂功能接入 AI 的正确姿势：拆层次 + 强验证闭环 + 人工审接口。

04 · Achievable Paths

两条可靠路径：验证自动化先行 · Agent 化闭环

经筛选聚焦风险收益比最优的两条主线：路径 01「验证自动化」收益确定、数周可见；路径 02「Agent 化设计闭环」是 2025–2026 研究主攻方向，投入大但上限高。原报告中的其余四条路线（个人教学、模块级 Copilot、领域模型私有化、厂商全流程 EDA）已移除——它们的价值要么并入这两条的执行细节，要么依赖这两条的成果。

01

06 · Gaps & Risks

六大瓶颈：为什么还不能全自动

每条瓶颈均附当前主流缓解手段。理解这些瓶颈，才能为团队选择正确的路径与预期。

1

幻觉与时序盲区

现象LLM 不懂时钟域、异步复位、跨时钟同步、时序收敛；语法正确但功能/时序错误率高。

缓解lint + 综合 + 形式验证自动化把关；PPA 感知生成方法（LLM-VeriPPA）；「生成→仿真→修复」闭环兜底。

2

基准饱和 vs 真实工程差距

现象VerilogEval/RTLLM 顶级通过率近 100%，但 RISC-V 整机评估显示集成、时序、面积等真实问题仍大量存在（IEEE 11570171）。

缓解以 ChipBench 与自建真实模块集为评估基线；用「全流程成功率」替代「单点通过率」做采购与立项决策。

3

工具反馈 Gap

现象Agent 拿不到仿真/综合工具的报错反馈，无法形成自我修正闭环——这是 Agent 化路径（路径 02）的最大卡点（Closing the Loop，IEEE 11534671）。

缓解优先自动化「反馈可获取」的环节（仿真、lint、覆盖率）；推动 EDA 工具开放结构化 API/日志接口。

4

验证成本转移而非消失

现象AI 生成代码仍需等价验证，且 AI 的「创新性 bug」更难定位；验证人力并未减少，只是从写代码转向审代码。

缓解让 AI 同时生成「代码 + 测试 + 断言」，把验证负担转给自动化回归；验证自动化（路径 01）先行。

5

数据与 IP 安全

现象芯片设计数据高度敏感，云端通用 API 有 IP 外泄风险，合规部门天然保守。

缓解私有化部署 + 内部 RAG；优先使用厂商私有云/国产方案（DeepSeek 系）；数据脱敏流程先行。

6

复合人才缺口

现象既懂 RTL/验证、又懂 LLM 工程（提示词、RAG、微调、评测）的工程师稀缺，「AI 生成的代码没人敢接」。

缓解以「个人学习 + 验证团队先行」双入口培养（验证工程师天然熟悉「证明正确性」）；建立内部 AI 评测与最佳实践库。

07 · Suggested Roadmap

给团队的落地路线图建议

一份保守但可执行的节奏：先用低风险路径建立量化认知，再决定是否投入重资产路径。

Phase 1

0 – 6 个月 · 验证自动化落地（路径 01）

  • 验证团队试点 AI 生成 UVM testbench / SVA 断言（AI Agents for UVM 等 2025.6 后实践思路），对比覆盖率达成时间与用例产出效率
  • 建立公司验证语料库：历史 testbench / 断言 → RAG 知识库，把 AI 输出与公司风格对齐
  • 量化基线：AI 用例直接采用率、覆盖率补洞速度、回归通过率，输出《验证自动化评估报告》
Phase 2

6 – 18 个月 · 单点 Agent 闭环（路径 02）

  • 打通 lint / 仿真报错回灌，把「testbench 生成 + 仿真修复」做成自动化闭环——这是 Agent 化最现实的第一步
  • 选择寄存器组、简单协议从机等边界清晰的模块，试点 Spec → RTL → 仿真 → 自修复
  • 用 ChipBench 级基准建立季度评测，跟踪「零人工干预成功率」与 pass@k，防流程退化
Phase 3

18 个月+ · 闭环扩展与规模化

  • Agent 闭环从单点模块扩展到子系统与协议模块，目标「零人工干预成功率」> 80%
  • 验证自动化从用例生成扩展到覆盖率分析与形式验证辅助，形成完整 AI 验证栈
  • 沉淀方法论：模块库 → 检索/训练数据 → 模型与流程迭代的飞轮；跟踪 Tool-Feedback Gap 研究进展（Closing the Loop）
08 · Playbook

实战方案：CBB Skill × AgentTeam 组装 SoC

面向「手头有大量已验证、但内部逻辑未完全掌握的闭源 CBB（通用构建模块）代码，想用多智能体团队完成大型 SoC 设计」的场景。核心理念一句话：别让 AI 写芯片，让 AI 组装芯片——把 CBB 封装成 AI 可调用的 Skill，LLM 只做规格拆解、互连装配与验证闭环，永不接触源码。

cbb-skill/
├── skill.json       # 功能摘要 / 适用场景 / 依赖关系（Agent 决策依据）
├── interface.json   # 接口契约：端口表(方向/位宽/协议) / 参数 / 时序约束 ← 最重要
├── template.sv      # 例化模板：Agent 填参数即可生成合法例化代码
├── testbench/       # 验证夹具：自检 bench（集成后自动验证正确性）
├── examples/        # 2-3 个完整可编译的典型用法
└── docs.md          # 行为说明 / 已知限制（黑盒分析 + 人工审核生成）

铁律：Agent 只读 skill.json / interface.json / template.sv / docs.md——.sv 源码永不进入 AI 上下文，通过「实例化 + 跑验证夹具」间接使用。

代码零外泄

闭源 CBB 源码只存在于内部沙箱服务器。Agent 通过工具调用间接使用：例化 → 仿真 → 拿结果，全程接触不到一行实现代码。IP 安全由架构保证，而非流程纪律。

黑盒契约驱动

「不理解功能也能安全用」：interface.json 的端口/时序契约 + 验证夹具保证正确性。功能描述可通过黑盒行为分析（自动激励扫描）+ LLM 辅助摘要生成，人工只需审核打勾。

验证夹具兜底

每个 Skill 自带自检 testbench。Agent 装配完模块即运行夹具，通过才算集成成功——「描述有偏差」不再可怕，错误会被仿真抓住并回灌修复。

版本治理

Skill 注册中心统一管理：CBB 升级 → skill 卡同步更新 → 全库回归测试。Agent 永远使用当前已验证版本，避免「旧 IP + 新流程」的隐性不匹配。

Phase 1

2–4 周 · PoC

  • 挑 3–5 个最常用 CBB 建 Skill 包（接口契约 + 验证夹具）
  • 单 Agent 试装最小 SoC：互连 + 2 个外设，跑通仿真
  • 产出：Skill 制作规范 + 首个可复现的 AI 装配 SoC
Phase 2

基础设施

  • 本地私有模型部署（DeepSeek 系开源模型，IP 不出域）
  • 内部仿真服务器 + Skill 注册中心（版本治理）
  • 黑盒行为分析流水线：自动生成功能卡草稿 + 人工审核
Phase 3

AgentTeam 化

  • 打通 lint / 仿真报错回灌（Tool-Feedback Gap 是核心工程）
  • Repair Agent 闭环：读报错 → 调参数/换配置 → 重跑
  • 多 Agent 并行例化模块，架构师 Agent 统筹互连与地址映射
Phase 4

规模化

  • Skill 库扩容至全部常用 CBB，覆盖 SoC 主要外设域
  • 验证自动化：Agent 生成 SoC 级 testbench / 断言 / 覆盖率补洞
  • 目标：完整 SoC 装配 + 回归通过，人工只审 Skill 卡与签核
1

Skill 卡错误 = 系统性误用

对策interface.json 与功能描述必须由资深工程师审核签名后方可上线；建立「Skill 评审 + 抽样回归」机制，CBB 升级强制全量回归。

2

IP 合规红线

对策闭源代码不进 prompt、Agent 执行沙箱化、本地私有模型推理；对外文档只暴露接口契约与验证报告，不暴露实现细节。

3

验证仍是硬门槛

对策SoC 级 testbench 质量决定成败——先搭互连与内存映射的验证骨架，再逐模块接入；Repair 闭环的报错信息结构化程度直接影响 Agent 修复成功率（参考 HWE-Bench 真实 bug 修复经验）。

一句话：别让 AI 写芯片，让 AI 组装芯片。用验证过的闭源 CBB 建 Skill 库（接口契约 + 例化模板 + 验证夹具），AgentTeam 负责规格拆解、互连装配、验证闭环——你只需审核每个 Skill 的接口契约。这是 2026 年 SoC 级 AI 落地中风险收益比最好的形态，与 Agentic EDA 的「Copilot → Agent」范式和 Design Conductor 的端到端验证互为印证。
