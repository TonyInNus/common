Redwood：一款由 AI 从零设计、验证并部署的前沿 AI 加速器

00 · Hint Point

观点速记（持续追加）

讨论中沉淀的观点按编号追加于此（H-01、H-02…），后续新观点继续补在列表末尾。

编号观点
H-01 性能模型是 AI agent 最便宜的试错环境。一次完整 RTL 迭代（生成+验证+综合）的算力成本远高于性能模型层迭代——AI 造芯的试错成本结构决定了：能在模型层筛掉的错误，绝不让它进 RTL 层。
H-02 搜索漏斗：先模型后 RTL。AI 探索微架构（如 Redwood SIMD 引擎数天的 PPA×覆盖率联合搜索）时，先在性能模型上筛掉明显差的候选，只为幸存者生成 RTL——把昂贵的 RTL 生成预算留给高潜力方案。
H-03 48 小时闭环的基石是分层验证。Redwood「规格变更 → 重验证 → 重部署 <48h」能成立，前提是每次变更的验证可先从性能模型层快速通过，而不是每次都从 RTL 全量重来——分层验证让迭代周期与变更规模解耦。
H-04 软件工程类比：性能模型 ≈ CI 冒烟测试（秒级反馈）；周期精确 RTL 仿真 ≈ 完整测试套件（分钟级）；FPGA ≈ 生产环境（实机，最慢但最真）。Redwood 的软件栈按此三级环境依次测试，越早的层迭代越快。
H-05 性能模型是"单一优化循环"的可执行起点。在 Redwood/ALP 流程里，规格之后第一份被 AI 生成、且之后每个环节（固件、内核、RTL、验证）都依赖的工件就是性能模型——它把人类规格变成可运行、可度量的东西，让"硬件-软件协同设计"从跨团队协调变成流程固有属性。
— 追加位：后续观点以 H-06、H-07… 续写于此 —
01 · The Thesis

它在论证什么：任务级提效 ≠ 程序级成果

Redwood 论文的出发点不是"AI 能写 RTL"，而是一个行业级矛盾——

A行业现状

  • EDA 行业宣称 AI 带来数量级提效：多月的 RTL/验证工作缩到数天、宣称 10× 生产力
  • 但 仅 14% 的 IC/ASIC 项目一次流片成功（20 年来最低），75% 延期（引用 2024 Wilson Research + SemiEngineering）
  • 结论：AI 加速了单个环节，却没有证明能改善复杂 SoC 的端到端结果

B核心主张

  • 机会不在"现有流程内做任务加速"，而在重写整个流程
  • 当架构、RTL、验证、固件、内核从同一份规格生成、在同一个目标下优化，顺序交接的延迟消失
  • 软硬件协同设计从"跨团队协调流程"变成系统的固有属性
  • 已有端到端 demo（小 RISC-V 核等）几乎都没在真实硬件上验证过——硬件才是设计的最终裁判
一句话立场：现代 AI 负载与硬件按不同时间尺度演化——架构定义领先量产硅片数年，而负载几个月就变。摩尔定律停滞下，专用化是每瓦性能的主要来源，设计周期必须跟得上负载的节奏。传统 9–12 个月的 ASIC 流水线做不到，所以要消灭 "freeze"。
02 · The AI System

AI 系统做了什么（Architect Labs Platform, ALP）

两位人类架构师写高层规格；规格以下是全自动的。验证方法学是全篇信息量最大的部分——没有任何人类 DV 工程师参与。

1自主产出物（两周）

  • 性能模型（先于 RTL 存在，支撑早期架构决策）
  • RTL 设计（零既有加速器 IP，从白纸开始）
  • UVM 验证环境 + SVA 断言 + 形式证明
  • 固件、驱动、自定义算子内核（FlashAttention / GEMM / GEMV）
  • 综合与物理设计就绪（timing closure）

2验证方法论（重点）

  • 对标行业实践：UVM + 形式化方法；开发了专有形式引擎，从人写规格生成验证环境的各个部分
  • 测试计划、testbench、用例、覆盖率闭合全自动——不是"人用 chat 指挥 agent"的形态
  • 论文口径：首个 RTL 上 FPGA 零 bug；验证环境至今没有一例"漏掉但被硬件抓出"的 bug

348 小时迭代循环

  • 规格即 source of truth；架构变体可并行探索（人和 agent 同时跑多方案）
  • 每次架构迭代：重新生成 → 重新验证 → 重新部署 FPGA，<48 小时
  • 仓库峰值一天 115 个 merge commit（负载上线与固件/内核持续优化期）
  • 全流程（规格 → RTL 定稿 + 验证 + 固件 + 内核 + 时序收敛）共两周；第三周跑通 Qwen3

4FPGA 复用环境

  • 自研仿真环境把 FPGA 访问复用给数百个并发 agent，连续数天无人干预地跑实验、分享性能结果、迭代
  • RTL/性能模型仿真 → FPGA 环境：单次优化从 15 小时缩到 15–30 分钟
  • AI 发现了人类专家没想到的优化与架构改进（含 SIMD 引擎数天级的 PPA×覆盖率联合搜索，候选可含全新控制通路/状态机，而非仅调位宽）
对"AI 写 RTL"叙事的颠覆：论文明确批评现有的"AI agent 验证"形态——"人用 chat 指挥 agent 做用例"仍然依赖大量人力、不随复杂度扩展、没有实质缩短端到端周期。他们的回答是让验证从规格自动生成，并且验证强度随算力扩展而非随人头/license 扩展。
03 · The Silicon

Redwood 芯片架构：为 transformer 推理协同设计的 tiled accelerator

用途：单批量、低功耗、超低延迟的 physical AI 推理（论文定义）。纯 AXI4 生态、可 chiplet 化、DMA 后端可重定向到 ACE/CHI。

ASoC 级设计选择

  • 接口纯 AXI4：AXI-Lite 控制 / 配置，宽 AXI4（满突发）传数据；DMA 后端可重定向 ACE/CHI 而不动计算面
  • 专用 DMA 引擎包办全部片外流量；GDMA 做片外↔LLC 的 bulk 搬运，edge DMA 做 tile 进出
  • 全局区：MCU 控制核 + 全局任务管理器 + 48-bit HAC 全局定时器（广播到每 tile，时间分片调度）
  • 内存接口集中在模块化 DMA → 可嵌大 SoC，也可独立 chiplet
  • 自研 credit-based NoC：低开销广播/组播、表驱动流重定向、逐链路流控

BTile 级：FE/BE 解耦

  • FE（控制/编程，慢时钟域）：RISC-V 微核 CRV（最小化实现、面积功耗低）+ CTM 任务管理器；kernel 执行期 FE 可关断
  • BE（数据/计算，快时钟域）：CMXM（脉动 GEMM/GEMV，INT MAC 阵列）+ CVXM（多 lane SIMD/FPU：reduction、LUT 等）
  • CRV 解码器与 BE 单元解耦——加/换 BE 单元不改 CRV；CRV 可把任务表交给 CTM 后休眠直到中断
  • 本 tile 512KB CMEM + 本地 ingress/egress DMA；FlashAttention-4 的 emulated-softmax 复用 SIMD 资源（省面积）
  • CTM 消息网络：跨核/跨 CTM 排序控制流，fire-and-forget 或 ack 模式；编译器用消息协调预取、双缓冲、乱序计算——把仲裁压力移进软件栈
编程模型（主机视角 5 步）：装载 DP set 与 kernel set → 主机写 dispatch ID + 操作数到 MCU DTCM → MCU 执行 DP（可编程路由表、配置预取/scatter-gather、launch tile kernel）→ DP 完成 → MCU 中断主机。模型太大装不下 ITCM 时按分区运行时装载并最小化换入换出。
04 · The Numbers

Redwood Nano = 2×2 tile 的 FPGA 配置（AMD Versal VPK180，250MHz），跑 Qwen3-0.6B。注意区分FPGA 实测与8nm 投影两条数据线。

1roofline 分析说了什么

  • Qwen3-0.6B：28 层、hidden 1024、16 Q-heads / 8 KV-heads、词表 151,936；INT8 线性层
  • 计算峰值：128 Gop/s（4 tile × 64 INT8 MAC lanes × 2）；SIMD BF16 8 Gop/s
  • 单层架构延迟 1.241 ms；整 token 理论上限 21.73 tokens/s（46 ms/token）
  • DRAM 服务时间 = 算术服务时间的 3.6× → decode 强内存受限（预期内）
  • 瓶颈在权重投喂链（DRAM→NoC→edge DMA→mesh→计算）的窄段：tile ingress

21 GHz 逻辑时钟的推演

  • FPGA 时序支撑 1 GHz 合理假设；DRAM 引脚速率固定不随 fabric 时钟缩放
  • 同带宽假设下 tile ingress 仍是最窄段（≈64 GB/s）→ 架构上限 ≈95 tokens/s
  • 最保守投影（执行与搬运无法完全重叠）：49 tokens/s，不改软件栈
  • 功耗估算：P_αCV²f 动态 ≈0.958W + 漏电 0.07W + 其余 SoC → 1.335W 上限（未计架构原生支持的时钟/电源门控收益）
05 · Recursive Self-Improvement

递归自我改进：论文最有野心的部分

把 Qwen3 部署到 Redwood 上并作为推理端点接入自家 AI 系统——然后让模型设计下一代跑它的硬件。

1已演示的

  • 反复采样后，模型发现了多个自身算子的时序改进与 kernel 优化，且零推理成本
  • 论文自称这是递归自我改进最早的演示之一：AI 设计了加速器 → 在它上面部署了 AI 模型 → 用该模型改进下一代加速器

2还差什么

  • 论文承认存在能力差：能自主设计硬件的 AI 系统，与能部署在该硬件上的 AI 模型，两者之间存在 gap
  • 愿景：弥合后，"AI 驱动的硬件持续改进"将成为 AI 进步的最大驱动力之一——他们声称这是递归自我改进最清晰的度量
06 · Critical Reading

诚实的审视：哪些地方要打问号

精讲不等于背书。以下是按论文原文口径整理的边界条件与未答问题——读任何"AI 造芯片"新闻前先看这一节。

1数据口径要分清

  • 12.1 vs 28 tokens/s 是 FPGA@250MHz vs GPU@1020MHz 的实测对比：频率差 4×、带宽差 4.25×——不是同工艺同频对比
  • 49 tokens/s / 3.4× PPA 是 Samsung 8nm 级工艺的投影（GE 估算 + 15% DFT + 70% 利用率 + 20% CTS 开销），不是硅片实测
  • 功耗 1.335W 是估算上限（作者明说未计门控收益）
  • "deployed" = AMD Versal FPGA 部署；论文展望未来工作才到 物理设计、tapeout、post-silicon——即尚未流片

2验证声明暂无第三方审计

  • "零 bug 逃逸"基于 自研验证流程 + 专有形式引擎的自证，无外部复现/审计
  • 95% 覆盖率是行业常规目标线（不是异常高）；覆盖对象与断言质量未公开细节
  • 测试负载单一：只有 Qwen3-0.6B 一个公开基准，尚未覆盖多样化负载

3可复现性

  • 系统组件（自训模型、agent 框架、AI-native EDA 工具、专有形式引擎）均未开源
  • 对比 DC/VerilogEval 系有公开 RTL/数据集，Redwood 目前只有论文 + 图
  • "115 merge commits/day" 可查证性有限（仓库未公开）

4但有一个硬事实无法忽视

  • 它在真实 FPGA 上跑通了真实 LLM（Qwen3-0.6B），包含完整链路：RTL+UVM+形式证明+固件+驱动+kernel
  • 这是继 Design Conductor（spec→GDSII 的 RISC-V，未上模型）之后，"AI 造芯"从 CPU demo 推进到 AI 加速器 + 真负载的一步
  • 48h 规格变更循环若为真，意味着硬件开发开始逼近软件迭代节奏——这才是论文真正想论证的事

读法：Redwood 不是 DC 的"更贵版本"，而是换了目标函数——DC 证明 spec→布局可达；Redwood 证明 从规格到可跑负载的整条软硬栈可由 AI 生成并闭环维护。两者共同的隐含前提：验证是端到端可信的根基（DC 靠仿真比对，Redwood 靠 UVM+形式引擎），这也再次印证主报告「验证先行」的判断。
08 · Takeaways

对芯片团队的三条启示

1端到端 AI 设计的边界条件已清晰

  • 可行前提：规格是唯一 source of truth + 全栈可自动再生成 + 验证强度随算力扩展
  • 代价结构：数百亿 token 级算力 + 专有 EDA/形式工具 + 大量并发 agent 基础设施——不是团队规模能补的

2对 CBB × AgentTeam 路线的启示

  • Redwood 证明"全自主从零"可行但昂贵；你的 CBB Skill 复用路线正是把该代价压回可控范围的策略（已验证 IP 免去全栈再验证）
  • 可借鉴其三点：验证产出全自动生成（而非人指挥 agent）、FPGA 复用环境给数百 agent 并行迭代、规格写法的"可度量性"决定产出质量

3关注其后续的可证伪点

  • 论文声明未来推进物理设计/tapeout/post-silicon——若兑现，8nm 投影可被硅片验证
  • 若验证方法与工具开源或接受第三方审计，"零 bug 逃逸"才可检验
  • 递归自我改进是"最早的演示"级别的声明——需要更多代际证据
